# 非機能要件

[要件定義書](./requirements.md) の詳細ドキュメント。X風SNSアプリの非機能要件をまとめる。

## 性能

- 想定する規模は数百ユーザー・数千投稿程度とする（受講生・個人の利用を想定）
- タイムライン・投稿詳細・プロフィール・検索結果の表示は、操作から画面反映まで体感的な遅延がないこと（目安：1秒以内）
- 一覧（タイムライン・コメント・フォロー一覧・検索結果）は20件ずつ、カーソル方式のページングで取得する（OFFSET を使わないので、件数が増えても後ろの方のページが遅くならず、読んでいる途中に投稿が増えても重複・抜けが起きない）。画面は下までスクロールすると自動で続きを読み込む（無限スクロール）
- タイムラインの新しい投稿は、60秒ごとに件数だけを確認して知らせる（常時接続はしない。確認は軽い件数の SQL だけで、ブラウザのタブが裏にある間は確認しない）
- いいね数・コメント数は一覧の取得時に1回の SQL でまとめて集計し、投稿1件ごとに SQL を発行しない（N+1問題を避ける）
- いいね・フォローのボタンは、API の結果を待たずに表示を切り替える（楽観的更新）
- 大量データ（数万ユーザー以上）での性能保証は対象外とする

## 可用性

- 基本的には開発者本人のローカル環境での起動・動作を想定する。AWS（ALB + EC2 + RDS）への構築は暫定案で、構築する場合も学習目的の一時的な稼働とする（詳細は[インフラ構成](./infrastructure.md)を参照）
- 常時稼働・高可用性構成（マルチAZ、EC2 の複数台構成等）は対象外とする
- 稼働率・障害復旧などのSLAは定義しない

## セキュリティ

- 認証は Spring Security + JWT で行う。ログイン成功時に、アクセストークン（JWT、有効期限15分）とリフレッシュトークン（有効期限14日）を発行する
  - アクセストークンは画面側のメモリにだけ持ち、リクエストのたびに `Authorization: Bearer <token>` を付ける。localStorage には保存しない（XSS で盗まれないように）
  - リフレッシュトークンは HttpOnly・SameSite=Strict の Cookie で渡し、DB にはハッシュだけを保存する。再発行のたびに新しいものに交換し、使用済みのものが使われたらそのユーザーのリフレッシュトークンをすべて無効にする
- パスワードは BCrypt でハッシュ化して保存する。平文では保存せず、ログにも出さない
- ログインに失敗したときは、メールアドレスとパスワードのどちらが違うかを教えない
- 投稿・コメントの編集や削除は、サーバー側で「本人のものか」を必ず確認する（画面でボタンを隠すだけにしない）
- 入力チェックはフロントとバックエンドの両方で行い、バックエンドのチェックを正とする
- DBへのアクセスは MyBatis で行い、値は必ず `#{}`（パラメータ化されたクエリ）で渡して SQLインジェクションを防止する。SQL に文字列をそのまま埋め込む `${}` は使わない。検索キーワードの `%` `_` はエスケープする
- ユーザー入力（投稿・コメント・プロフィール）を画面に表示する箇所ではXSS対策（React の標準のエスケープに任せ、`dangerouslySetInnerHTML` は使わない）を行う
- アップロードされた画像は、拡張子ではなくファイルの中身で形式を判定する。ファイル名は UUID に置き換える
- S3 のバケットは公開せず、画像は CloudFront 経由でだけ配信する。AWS 上のサーバーから S3 へは IAM ロールで接続し、アクセスキーをサーバーに置かない
- DB のパスワードや JWT の署名鍵はソースコードに書かず、環境変数で渡す。Git にもコミットしない
- インターネットに公開する場合は HTTPS を必須とする（パスワードと JWT を送るため）

## 保守性・拡張性

- 将来的な機能追加（通知、投稿検索等）を見据え、フロントエンド・バックエンドともにコンポーネント／レイヤー単位で責務を分離した設計とする
- 投稿カード・ユーザーへのリンク・フォローボタンなど、複数画面で使う部品は共通化する
- 画像の保存処理はインターフェースで分け、S3（本番）と LocalStack（開発）を設定で切り替えられるようにする
- TypeScript の型定義により、API のレスポンスとフロントのデータ構造の一貫性を保つ

## ユーザビリティ

- 主要な操作（投稿・いいね・コメント・フォロー）は3クリック以内で完了できることを目安とする
- 破壊的な操作（投稿削除・コメント削除）には確認ダイアログを設ける
- 送信中のボタンは押せないようにし、二重送信を防ぐ
- 画面ごとに URL を分け、リロード・ブラウザの「戻る」・URL の共有で同じ画面が表示されるようにする

## 互換性

- フロントエンドは Google Chrome の最新版で動作することを必須とする
- PCでの利用を優先する。スマートフォンでは表示が崩れない程度に対応する
- バックエンド・DBは開発者本人のローカル環境（Mac）で動作すること（バックエンド：Java 25 + Spring Boot 4.1、DB：PostgreSQL 17。詳細は[技術スタック](./tech-stack.md)を参照）

## データ永続性・信頼性

- データベース（PostgreSQL）と S3 により永続化し、ブラウザやアプリを閉じてもデータが失われないこと
- いいね・フォローの重複はDBの一意制約で防ぎ、ボタンの連打や通信の再送があっても数がずれないこと
- 投稿を削除したときは、関連する画像・コメント・いいねも削除し、不整合を残さないこと
- バックアップ・エクスポート機能は今回のスコープ外とする
- DBのスキーマ変更（マイグレーション）は Flyway で管理する

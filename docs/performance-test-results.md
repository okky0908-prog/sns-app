## 2026-11-06 #131 の改善のあと：ユーザー検索（ローカル）

`users` の `username`・`display_name` に、pg_trgm の GIN 索引を作った（#131、`V9__add_user_search_index.sql`）。データは 10 倍（5,000 人）。

### 検索の SQL だけの時間（`EXPLAIN ANALYZE`、5 回の中央値）

| キーワード | 当てはまる人 | 索引なし | 索引あり | 索引を使ったか |
|---|---|---|---|---|
| `perf0042` | 10 | 3.71ms | **0.12ms** | 使った（Bitmap Index Scan） |
| `perf001` | 100 | 3.55ms | 3.63ms | 使わない（全件を読むほうが速いと判断） |
| `性能テスト 1` | 1,111 | 3.98ms | 4.07ms | 使わない（同上） |
| `性能` | 5,000（全員） | 7.7ms | 9.0ms | 使えない（2 文字なので 3 文字の組を作れない）。この行だけ並べ替えを含む SQL の 1 回の値で、差はぶれの範囲 |

- 当てはまる人が少ないキーワードでは、約 30 倍速くなった
- 当てはまる人が多いキーワードでは、PostgreSQL が全件を読むほうを選ぶので変わらない。テストデータは全員の名前が `perfNNNNN`・`性能テスト N` とそろっていて、当てはまる人が多くなりやすい。実際の SNS では名前がばらばらなので、索引が効く検索が多くなると考えられる

### ストレス（10 倍、500 人まで）での比較

k6 は 6 つのキーワードから選んで検索する（`perf`・`perf001`・`perf0042`・`性能`・`テスト`・`性能テスト 1`）。このうち索引が効くのは `perf0042` だけ。

| 値 | 前（初回） | 後 |
|---|---|---|
| 検索の SQL の平均 / 最大（`pg_stat_statements`） | 10.5ms / 58.2ms | **7.9ms / 40.1ms** |
| 検索の SQL の合計時間 | 20.2 秒（1,924 回） | **14.7 秒**（1,859 回） |
| `GET /api/users/search` の p95 / 最大 | 24.7ms / 165ms | 25.3ms / 61ms |
| 全体の p95 | 10.6ms | 12.4ms |
| 通信の失敗（`dial: i/o timeout`） | 4 件 | 9 件 |

- 検索の SQL の合計時間は 3 割ほど減った。それでも合計時間の 1 位のまま。残りは、全員が当てはまるキーワードで 5,000 人を並べ替える時間
- API の p95 は変わらない。全体の p95 のわずかな差は、測るたびのぶれの範囲と考える（今回はバックエンドを起動した直後から測った）
- 通信の失敗は、初回と同じく Docker Desktop の中継の部分の時間切れで、バックエンドには届いていない

## 2026-11-06 #130 の改善のあと：ログイン集中（ローカル）

ログイン・新規登録で、BCrypt をトランザクションの外に出した（#130）。条件は初回と同じ（ログイン集中・基準のデータ）。起動した直後は JIT が効く前で値がぶれるので、1 回流して温めてから測った値を使う。

最初の 30 秒（裏で操作する 20 人と監視役が、一斉にログインする時間）の比較。

| 値 | 前（初回） | 後 |
|---|---|---|
| 接続待ちの最大 | 7 | **0** |
| 接続使用の最大 | 10 | 10 |
| ログイン以外の API の p95 / p99（ms） | 16.9 / 75.8 | 20.8 / **31.0** |
| 20 人のログインの p50 / 最大（ms） | 119 / 258 | 286 / 337 |
| 1 分以降のログインの p95（ms、20 件/秒） | 81.9 | 88.8 |
| エラー率 | 0% | 0% |

- ログインが集中しても、ほかの API が接続を待たされなくなった（p99 が 76ms → 31ms）
- 一斉にログインしたときの、ログインそのものの時間は長くなった。これまでは接続プール（10 本）が、同時に動く BCrypt を結果的に 10 件までに抑えていた。それがなくなり、20 件が同時に CPU を取り合うようになったため。BCrypt は CPU だけを使うので、処理できる件数は変わらない
- t3.micro（2 vCPU）では CPU の取り合いがもっと大きくなる。手順 5 で、一斉にログインしたときの時間と CPU を確かめる。必要なら、同時に動かす BCrypt の数を絞ることを考える

### 測定の途中で直したこと

- **k6 が繰り返しのたびに Cookie を消していた**：1 回目の耐久テストで、トークンの再発行が 21,512 回すべて 401 になり、15 分を過ぎてからのリクエストもすべて失敗した。k6 は既定で、1 回の繰り返しが終わるたびに VU の Cookie を消す（`noCookiesReset: false`）。そのため、ログインのときに受け取ったリフレッシュトークンの Cookie が、再発行のときには残っていなかった。アプリの不具合ではない。すべてのシナリオに `noCookiesReset: true` を付け、14 分を超えるシナリオ（ストレス・耐久）を測り直した。上の表は測り直したあとの値

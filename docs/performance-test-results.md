## 2026-11-11 #176 の改善のあと：ログイン集中（AWS）

BCrypt（パスワードの照合・ハッシュ化）を同時に 1 件までにし、空きを 1 秒待っても空かなければ 503（`SERVER_BUSY`）ですぐ返すようにした（#176）。条件は下の「AWS での測定」と同じ（ログイン 20 件/秒・5 分、裏で 20 人がふつうに操作。コミット `0b1bb25`）。

| 値 | 前 | 後 |
|---|---|---|
| ふつうの操作の p95（全体） | 60 秒（時間切れ） | **1.2 秒** |
| ふつうの操作の p95（1 分以降） | — | **0.12〜0.15 秒** |
| ふつうの操作のエラー率（全体 / 1 分以降） | 14.0% / — | 12.7% / **0%** |
| ログインの p95 | 30 秒（時間切れ） | **1.4 秒** |
| 成功したログイン | — | 972 件（約 3.2 件/秒） |
| ログインの 503（混み合っている） | — | 4,457 件（82%）。どれも約 1.1 秒で返った |
| 始められなかったログイン | 2,420 回 | **0 回** |
| API の CPU | 最大 100%・平均 80% | 最大 100%・平均 100% |

- 処理できない分のログインを、約 1.1 秒（空きを待つ 1 秒＋往復）で 503 にして返すようになり、**ふつうの操作が止まらなくなった**（1 分以降はエラー 0%、p95 は 0.15 秒以下。ふだんの 0.03〜0.05 秒よりは遅い）
- CPU は 100% のまま。BCrypt を 1 件ずつにしても、その 1 件が 0.5 vCPU を使い切るため。ほかの API が動けるのは、CPU の順番待ちの相手が BCrypt の 1 件だけになったから
- 最初の 1 分のエラー（ふつうの操作の 298 件の 503）は、裏で操作する 20 人のログインが、集中しているログインと一緒に 503 になったもの。ログインし直せたあとは、エラーは出ていない。ログインが集中している間は、新しくログインする人も「混み合っています」と表示されて、少し待つことになる
- 1 秒にこなせるログインの数（約 3 件）は変わらない。増やすには、タスクの CPU を増やす（または台数を増やす）必要がある

### ログイン集中（5 分。裏で 20 人がふつうに操作）

ログインの回数を、計画書の 20 件/秒と、API が持ちこたえた 3 件/秒の 2 通りで流した（`RATE=3 perf/run.sh login`）。

| ログインの回数 | ログインの p95 | ふつうの操作の p95 | エラー率（ログイン / ふつう） | 始められなかったログイン | API の CPU |
|---|---|---|---|---|---|
| 20 件/秒 | 30 秒（時間切れ） | 60 秒 | 85.2% / 14.0% | 2,420 回 | 最大 100%・平均 80% |
| 3 件/秒 | 611ms | 592ms | 0% / 0% | 0 回 | 最大 99.9%・平均 87.7% |

- 20 件/秒では、10 秒ごとに見ると、まだ 1.8 件/秒の時点でログインの p50 が 3.5 秒になっていた。BCrypt（コスト 10）の照合は、0.5 vCPU のタスクでは 1 件あたり CPU を約 0.15 秒分使う（3 件/秒で CPU が平均 88%）ので、こなせるのは 1 秒に 3 件ほど。それを超えた分は CPU の順番待ちになり、**ログイン以外の API まで待たされて時間切れになった**
- 3 件/秒では、最初の 1 分（裏の 20 人が一斉にログインする）に全体の p95 が 4.2 秒まで伸び、1 分以降はログインの p95 が約 340〜540ms、ふつうの操作の p95 が約 100ms に落ち着いた
- ローカルの初回の予想（「2 vCPU で CPU 75% 以上」）より厳しい結果になった。ふだんの利用ではここまで集中しない（ログイン状態はリフレッシュトークンで 14 日続く）が、たくさんのメールアドレスで試す総当たり攻撃を受けると、アプリ全体が使えなくなる → **#176**（同時に動かす BCrypt の数を絞り、空きがなければ 503 ですぐ返す）

## 2026-11-08 CLS（レイアウトのずれ）を足した（ブラウザ・ローカル）

ブラウザのパフォーマンステストに CLS を足した（#151）。基準の規模のデータ、5 回の中央値（最大も同じ値）。

| 測るもの | Mac のまま | 遅い端末・回線のまね | 目安 | 合否 |
|---|---|---|---|---|
| ログイン画面：レイアウトのずれ（CLS） | 0.007 | 0.007 | 0.1 | 合格 |
| タイムライン（再訪問）：レイアウトのずれ（CLS） | 0.016 | 0.016 | 0.1 | 合格 |

- どちらも目安の 1/6 以下。ずれの元を `layout-shift` の `sources` で調べると、どちらも約 15px のずれだった：
  - ログインの確認中・タイムラインの読み込み中に出す「読み込み中…」の段落の上の余白（1em = 15px）が `body` の外に出ていて（余白の相殺）、本物の画面に置き換わると全体が 15px 上に動く
  - → **#153 で直した**：読み込み中・お知らせの `<p>` の余白を 0 にした（間隔はもとからある `padding` で取る）。直したあとは、2 つの条件とも、ログイン画面・タイムラインの CLS が **0.000**（5 回とも）
- 計測の確かめ：読み込みの 0.3 秒後に、画面の上に高さ 200px の帯を差し込むと 0.049・0.084（合格のまま）、400px にすると 0.104・0.160 で、目安を超えて落ちた

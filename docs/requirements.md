# 要件定義書：X風SNSアプリ

## 1. 概要

X（旧Twitter）のような、タイムライン形式のテキスト中心のSNS風Webアプリケーション。
スクール課題として開発する。複数のユーザーが投稿し、互いにいいね・コメント・フォローし合うことを前提とする。

## 2. 背景・目的

- 本プロジェクトはスクールの課題として取り組むものであり、特定の業務課題やビジネス上の目的があるわけではない
- 主目的は学習：要件定義〜設計〜実装という開発の一連の流れを、前回のタスク管理アプリ（`github-demo`）より一段複雑な題材で経験すること
  - 前回はなかった、ログイン認証・複数ユーザー・多対多のリレーション（いいね・フォロー）・集計（いいね数・コメント数）・画像アップロード（S3）・検索を扱う
- 利用者は受講生・個人だが、**第三者からのいいね・コメントがあり得る**ため、各投稿にいいね数・コメント数を表示する
- X/Twitter との差別化として、次の2点を設ける
  - **インプレッション数（表示回数）を表示しない**：数字を競う雰囲気を避け、やり取りそのものに集中できるようにする
  - **リツイート（リポスト・引用）機能を用意しない**：投稿は投稿者のプロフィールとタイムラインにだけ表示される

## 3. 想定利用者

- 受講生・個人（複数ユーザー）
- 利用にはアカウント登録・ログインが必要。未ログインで使えるのはログイン画面と新規登録画面のみ
- 管理者（ユーザーの凍結、投稿の強制削除など）は想定しない

## 4. スコープ

### 4.1 今回実装する範囲（MVP）

- 新規登録・ログイン・ログアウト（アクセストークン＋リフレッシュトークンによる認証）
- 投稿の作成（280文字のテキスト＋画像4枚まで）・編集・削除・詳細表示
- タイムライン（フォロー中タイムライン・全体タイムライン）
- コメントの投稿・一覧・削除、コメント数の表示
- いいね・いいね取り消し、いいね数の表示
- フォロー・フォロー解除、フォロー中・フォロワー一覧、フォロー数・フォロワー数の表示
- プロフィールの表示・編集（表示名・自己紹介・アイコン画像）
- ユーザー検索（`@ユーザー名`・表示名の部分一致）

### 4.2 将来的に追加したい範囲（今回は対象外）

- 通知（いいね・コメント・フォローされたとき）
- 投稿の検索、ハッシュタグ
- コメントへの返信（スレッド）、コメントへのいいね
- 「おすすめユーザー」の表示（フォロー中の人がフォローしている人など）
- パスワードリセット、メールアドレス確認、パスワード変更
- 退会（ユーザー削除）
- いいね数・コメント数をカウンタ列で持つ方式への切り替え（データが増えた場合）

### 4.3 明確に対象外とするもの

- リツイート・引用（差別化のため、今後も追加しない）
- インプレッション数の表示（差別化のため、今後も追加しない）
- ダイレクトメッセージ
- 非公開アカウント、ブロック・ミュート
- 管理者機能

## 5. 機能要件

認証・投稿・タイムライン・コメント・いいね・フォロー・プロフィール・ユーザー検索の8分類、25機能（F-01〜F-71）で構成する。投稿は本文280文字・画像4枚まで、タイムラインは「フォロー中」と「全体」の2種類、いいね・フォローは1人1回まで（DBの一意制約で保証）とする。ユーザーの名前はどこでもクリックでプロフィールへ移動でき、そこからフォローできる。

→ 詳細は [機能要件](./features.md) を参照

機能ごとの処理の流れ・エラー時の動き・受け入れ条件は、→ [機能定義書](./feature-specs/README.md) を参照

## 6. 画面仕様・画面遷移・ユースケース

React Router による複数画面構成（SPA）とし、ログイン・新規登録・タイムライン・投稿詳細・プロフィール・プロフィール編集・フォロー一覧・ユーザー検索の8画面と、投稿作成／編集モーダルで構成する（S-01〜S-10）。投稿カード（いいね数・コメント数を表示し、インプレッション・リツイートのボタンは置かない）とユーザーへのリンクは全画面で共通の部品とする。

→ 詳細は [画面仕様・画面遷移・ユースケース](./screens.md) を参照

## 7. 非機能要件

性能・可用性・セキュリティ・保守性・ユーザビリティ・互換性・データ永続性の観点で定義する。前回と違いログイン機能を持つため、認証（JWT）・パスワードのハッシュ化・本人確認（他人の投稿を編集・削除できない）などのセキュリティ要件を追加する。

→ 詳細は [非機能要件](./non-functional-requirements.md) を参照

## 8. データ構造・ER図

users・posts・post_images・comments・likes・follows と、ログイン状態を保つための refresh_tokens の7テーブルで構成する。いいね（users と posts）とフォロー（users 同士）は多対多の関係で、中間テーブルに一意制約を付けて重複を防ぐ。いいね数・コメント数・フォロー数は列として持たず、表示のたびに集計する。画像ファイルは S3 に保存し、DB には S3 のキーだけを持つ。

→ 詳細は [データ構造・ER図](./database.md) を参照

フロントエンド〜バックエンド間の API（REST・JSON）は → [API設計](./api.md) を参照

## 9. 技術スタック

前回のタスク管理アプリと同じ技術は同じバージョンを使う。フロントエンドは React 19 + TypeScript 7 + Vite 8（React Router を追加）、バックエンドは Java 25 + Spring Boot 4.1（Spring Security + JWT を追加）、DB は PostgreSQL 17（MyBatis + Flyway）、画像は Amazon S3 を採用する。

→ 詳細は [技術スタック](./tech-stack.md) を参照

## 11. インフラ構成（AWS）

画像の保存先に S3（配信は CloudFront）を使うことは決定済み。アプリのサーバーを AWS 上に構築する場合は、前回の EC2 + RDS 構成に ALB を加えた構成（ALB + EC2 + RDS for PostgreSQL 17、Terraform で構築）とする。現時点では暫定案。

→ 詳細は [インフラ構成](./infrastructure.md) を参照

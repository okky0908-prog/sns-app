# テスト計画書

このアプリの自動テストを、どの層で・どの技法で・どんなケースを作るかを決める。テストを書くときは、この計画書の技法でケースを洗い出し、PR に「使った技法と作ったケース」を書く（[CLAUDE.md](../CLAUDE.md)「テスト駆動開発（TDD）のルール」）。

## 1. 目的と範囲

| 目的 | 内容 |
|---|---|
| 壊れていないことを自動で確かめる | 毎回ブラウザで手で確かめなくても、`./gradlew check` と `npm test` で分かるようにする |
| 変更の安全網にする | 機能の追加・整理・ライブラリの更新のあとに、動きが変わっていないと言えるようにする |
| 仕様を記録する | テストの名前と中身を読めば、仕様（境界・エラーの条件）が分かるようにする |

- 対象：バックエンド（Mapper・Service・Controller）、フロントエンド（関数・通信・UI 部品・画面）
- 対象外：性能・負荷のテスト（[非機能要件](non-functional-requirements.md)で数万ユーザー以上は対象外）、AWS 上の環境（未構築）

## 2. テストの技法

テストのケースは、**ブラックボックステストで設計し、ホワイトボックステストで漏れを確かめる**。

```
① 仕様（機能定義書・API設計）── ブラックボックスの技法 ──▶ ケースを設計してテストを書く
② コード ─────────────────── カバレッジを測る ────────▶ 通っていない分岐を見つける
③ 通っていない分岐が「仕様の漏れ」か「不要なコード」かを判断し、ケースを足す（または、コードを消す）
```

### 2.1 ブラックボックステスト（中身を見ず、仕様の入力と出力から考える）

| 技法 | 考え方 | このアプリで使う場面 |
|---|---|---|
| **同値分割** | 入力を「同じ扱いになるグループ（同値クラス）」に分け、各グループから代表を1つ選ぶ。有効なグループと無効なグループの両方を選ぶ | 入力チェック（文字数・形式）、画像の形式（jpg・png・gif／それ以外） |
| **境界値分析** | グループの境目（最小・最大・その1つ外）を必ず確かめる。不具合は境目に集まる | 文字数の上限・下限、画像の枚数、期限ちょうど、1時間ちょうど |
| **デシジョンテーブル** | 条件が複数あるとき、条件の組み合わせと結果を表にし、表の列ごとにケースを作る | 投稿の作成・編集、権限（本人か）、エラーの優先順位 |
| **状態遷移テスト** | 状態と、状態を変えるできごとを図にし、すべての遷移と「起きてはいけない遷移」を確かめる | リフレッシュトークン、いいね・フォロー、画面のログイン状態 |
| **エラー推測** | 経験から「壊れやすい所」を予想してケースを足す | 絵文字・改行（`\r\n`）・空白だけ・null・大文字小文字・`%` `_` `\`・同時の操作・タイムゾーン・外部（S3）の失敗 |

### 2.2 ホワイトボックステスト（コードの中身を見て、通る道を考える）

| 網羅の基準 | 意味 | この計画での扱い |
|---|---|---|
| **命令網羅（C0）** | すべての行を1回以上通す | 最低限の目安 |
| **分岐網羅（C1）** | すべての分岐（if の真と偽、三項演算子、`?.` など）の両方を1回以上通す | **主な目標**（6章の基準） |
| **条件網羅** | `a && b` の a・b それぞれの真偽を通す | 条件が2つ以上ある if（例：`text.isEmpty() && uploads.isEmpty()`）はケースを足す |
| パス網羅 | 分岐のすべての組み合わせを通す | 組み合わせが爆発するので目標にしない。重要な組み合わせはデシジョンテーブルで選ぶ |

- カバレッジ（どれだけ通したか）は道具で測る：バックエンドは **JaCoCo**、フロントは **Vitest の coverage（v8）**
  - バックエンド：`./gradlew test` のあとに `backend/build/reports/jacoco/test/html/index.html` ができる（通っていない分岐が色で分かる）
  - フロント：`npm run test:coverage` で `frontend/coverage/index.html` ができる
  - 層ごとの表：`python3 scripts/coverage-summary.py <CSV か JSON>`（CI はジョブの概要に出し、HTML のレポートを保存する）
- カバレッジは「テストの量」ではなく「**漏れを見つける道具**」として使う。数字を上げるためだけのテスト（結果を確かめないテスト）は書かない

### 2.3 テストが本当に見張っているかの確認

- 新しく作るコード：テスト駆動の **Red**（先に失敗を確かめる）で確認する
- すでにあるコード：コードをわざと壊して（例：`<` を `<=` にする）、テストが落ちることを確かめる（ミューテーションの確認）。PR に「壊した内容と落ちたテスト」を書く

## 3. テストの層

速くて安い単体テストを多く、遅い結合・E2E テストは大事な流れに絞る（テストのピラミッド）。

| 層 | 対象 | 道具 | DB・外部 | 確かめること | 主な技法 |
|---|---|---|---|---|---|
| **Mapper** | 7つの Mapper（SQL） | `@MybatisTest` + Testcontainers | 本物の PostgreSQL（使い捨て） | SQL が正しく読み書きできるか。並び順・絞り込み・件数・一意制約・`ON CONFLICT`・NULL の扱い | 同値分割・境界値（ページの区切り）・エラー推測（大文字小文字・LIKE の特殊文字） |
| **Service** | 10の Service | JUnit + Mockito（Spring なし） | Mapper・S3 は偽物（モック） | 判断の分岐・エラーの種類・呼び出す Mapper と引数・時刻の扱い | デシジョンテーブル・状態遷移・境界値。**分岐網羅（C1）の主な対象** |
| **Controller** | 7つの Controller（26の API） | `@WebMvcTest` + `@MockitoBean` | Service は偽物 | URL・メソッド・ステータス・入力チェック（`@Valid`）・認証の要否・JSON の形・エラーの形式 | 同値分割（入力チェック）・デシジョンテーブル（認証×権限） |
| **結合** | API から DB まで通し | `@SpringBootTest` + MockMvc + Testcontainers | 本物の PostgreSQL・LocalStack | 部品をつないだときの動き（トランザクション・後片付け・N+1） | 今あるテスト（165件）を残す。上の単体テストと重なる細かいケースは、単体テストへ寄せる |
| **フロントの関数・通信** | `lib/`・`api/client.ts`・`auth/validation.ts`・フック | Vitest | `fetch` は偽物 | 計算・判定・トークンの再発行とやり直し・エラーの変換 | 境界値・状態遷移・分岐網羅 |
| **UI 部品** | 15の部品（`components/`） | Vitest + Testing Library + jsdom | API は偽物 | 表示・ボタンの有効／無効・押したときの変化・エラーの表示・アクセシビリティ（ラベル） | 同値分割・状態遷移（押す前・通信中・成功・失敗） |
| **画面** | 8つの画面（`pages/`） | Vitest + Testing Library | API は偽物 | 読み込み中・空・エラー・一覧の表示、画面の移動 | 状態遷移 |
| **E2E** | 主要な流れ（`frontend/e2e/`） | Playwright + `./gradlew bootTestRun` | すべて本物（PostgreSQL・LocalStack は使い捨てのコンテナ） | 画面とサーバーをつないだときの動き（Cookie でのログインの維持・画像の保存と配信・読み込み直しても残るか） | 大事な流れだけ（9.9） |

## 4. ケースの設計例（このアプリに当てはめたもの）

### 4.1 同値分割と境界値分析：入力チェック

文字数は、前後の空白・改行を除き、コードポイントで数える（絵文字も1文字）。

| 項目 | 有効なグループ | 無効なグループ | 境界値として必ず確かめる値 |
|---|---|---|---|
| 投稿の本文 | 0〜280文字（画像があるとき）、1〜280文字（画像がないとき） | 281文字以上 | 280・281、空白だけ（→ 0文字）、絵文字280個、`\r\n` を含む |
| 投稿の画像 | 0〜4枚、jpg・png・gif、1枚5MB以下 | 5枚以上、それ以外の形式、5MB超 | 4・5枚、5MB ちょうど・5MB+1バイト、拡張子は png だが中身が gif |
| コメント | 1〜280文字 | 0文字、281文字以上 | 0・1・280・281 |
| ユーザー名 | 半角英数字と `_` で4〜15文字 | 3文字以下、16文字以上、それ以外の文字、`search` | 3・4・15・16、`-` を含む、全角 |
| 表示名 | 1〜50文字 | 0文字（空白だけを含む）、51文字以上 | 0・1・50・51、絵文字50個 |
| 自己紹介 | 0〜160文字 | 161文字以上 | 160・161、空（→ null で保存） |
| パスワード | 8〜72文字 | 7文字以下、73文字以上 | 7・8・72・73 |
| 検索キーワード | 0〜50文字（前後の空白と先頭の `@` を除いて数える） | 51文字以上 | 50・51、`@` だけ、空白だけ |
| 新しい投稿の件数 | 0〜100件 | — | 0・99・100・101件（100件で数えるのをやめる） |
| 一覧のページ | 1ページ20件 | — | 19・20・21件（続きの有無が変わる） |

### 4.2 デシジョンテーブル：投稿の作成（A-11）

| 条件 ＼ ケース | 1 | 2 | 3 | 4 | 5 | 6 |
|---|---|---|---|---|---|---|
| 本文が280文字以下 | Y | Y | Y | N | Y | Y |
| 本文がある（空白を除いて1文字以上） | Y | N | Y | Y | N | Y |
| 画像がある | N | Y | Y | − | N | Y |
| 画像が4枚以下 | − | Y | Y | − | − | N |
| **結果** | 作成 | 作成（本文は空） | 作成 | 400 `content`（長すぎ） | 400 `content`（本文か画像が必要） | 400 `images`（多すぎ） |

- 「−」はその条件を見ない（ほかの条件で結果が決まる）
- エラーが複数当てはまるときの優先順位（文字数 → 枚数 → 形式 → 本文か画像の有無）も、ケースを足して確かめる
- S3 への保存に失敗したとき（500 `IMAGE_UPLOAD_FAILED`。それまでに保存した画像は消し、投稿は作らない）は、エラー推測のケースとして足す

### 4.3 デシジョンテーブル：投稿の編集（A-13）

| 条件 ＼ ケース | 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|
| 投稿がある | N | Y | Y | Y | Y |
| 自分の投稿 | − | N | Y | Y | Y |
| 新しい本文が空 | − | − | Y | Y | N |
| 画像がある | − | − | N | Y | − |
| **結果** | 404 | 403 | 400（画像のない投稿は空にできない） | 更新 | 更新（本文が同じなら「編集済み」を付けない） |

### 4.4 状態遷移：リフレッシュトークン（A-04）

```
            発行（ログイン・新規登録・再発行）
                     │
                     ▼
   ┌──────────── 有効 ────────────┐
   │再発行で交換     │ログアウト     │期限が切れる
   ▼                 ▼               ▼
 交換済み         ログアウト済み    期限切れ ──(毎日4時)──▶ 削除済み
   │ 10秒以内にもう一度使う → 新しいトークンを発行（同時のリクエスト）
   │ 10秒を過ぎてもう一度使う → そのユーザーのトークンをすべて無効（使い回しの検知）
```

| 今の状態 | できごと | 期待する結果 |
|---|---|---|
| 有効 | 再発行 | 200。古いものは交換済み、新しいものを発行 |
| 交換済み（10秒以内） | 再発行 | 200（全無効化しない） |
| 交換済み（10秒より後） | 再発行 | 401。そのユーザーのトークンをすべて無効 |
| ログアウト済み | 再発行 | 401。すべて無効 |
| 期限切れ（期限ちょうどを含む） | 再発行 | 401 |
| 削除済み・知らないトークン | 再発行 | 401（全無効化は起きない） |
| どれでも | ログアウト | 204（Cookie がなくても 204） |

同じ考え方で、**いいね・フォロー**（未 → 済 → 未。済で POST・未で DELETE しても状態は変わらずエラーにならない）と、**フロントのログイン状態**（アクセストークンが期限切れ → 再発行 → やり直し、再発行も失敗 → ログイン画面）の遷移表も作る。

### 4.5 エラー推測：壊れやすい所のチェックリスト

- 文字：絵文字・つないだ絵文字（家族など）・改行 `\r\n`・全角スペース・空白だけ・null・空文字
- 検索：大文字と小文字（`Yamada` と `yamada`）、LIKE の特殊文字（`%` `_` `\`）、先頭の `@`
- 時刻：期限ちょうど、日付の変わり目（UTC と日本時間）、未来の日時（端末の時計のずれ）
- 同時の操作：いいねの連打、2つのタブからの同時の再発行
- 外部の失敗：S3 に保存できない、DB の保存が取り消された（保存した画像を消す）
- 権限：他人の投稿・コメントの編集・削除、ログインなしでの呼び出し、トークンの改ざん
- 一覧：0件、ちょうど20件、21件、削除された投稿を含む

### 4.6 ホワイトボックス：`PostService.create` の分岐網羅（C1）

| 分岐 | 真になるケース | 偽になるケース |
|---|---|---|
| `content == null` | 本文なし（画像だけ） | 本文あり |
| `images == null` | 画像のパートなし | 画像あり |
| `!file.isEmpty()` | 中身のある画像 | 空のファイル（除外される） |
| 文字数 > 280 | 281文字 | 280文字 |
| 枚数 > 4 | 5枚 | 4枚 |
| `text.isEmpty() && uploads.isEmpty()` | 本文も画像もない | 本文だけ／画像だけ（条件網羅で両方） |
| `storeAll` の例外 | 2枚目の保存で失敗（1枚目を消す） | すべて保存できる |
| `!keys.isEmpty()` | 画像あり（画像の行を入れる） | 画像なし |

デシジョンテーブル（4.2）のケースで、ほとんどの分岐が通る。通らなかった分岐（空のファイル・保存の失敗など）をケースとして足す。

## 5. 部品ごとのテストの対象と観点

### 5.1 Mapper（7つ・SQL 44本）

| Mapper | 主な観点 |
|---|---|
| UserMapper | 登録・一意制約（ユーザー名・メールアドレス）・大文字小文字を区別しない検索・検索の並び順（完全一致 → 前方一致 → それ以外）・LIKE の特殊文字・最近参加したユーザーのカーソル |

| CommentMapper | 古い順とカーソル・コメント数・削除 |
| LikeMapper | `ON CONFLICT` で2回目の登録が増えない・取り消し・件数 |
| FollowMapper | `ON CONFLICT`・自分自身のフォローを DB の制約で防ぐ・フォロー中／フォロワー一覧の並びとカーソル |
| RefreshTokenMapper | ハッシュでの検索・無効化（すでに無効なら 0件）・交換・全無効化・期限切れの削除 |

### 5.3 Controller（7つ・26の API）

すべての API で、次の基本ケースを作る（デシジョンテーブル：認証 × 入力 × 結果）。

| ケース | 期待する結果 |
|---|---|
| 正しい入力・ログイン済み | 正しいステータス（200・201・204）と JSON の形 |
| ログインなし（ログインが必要な API） | 401 `UNAUTHENTICATED` |
| 入力チェックの違反 | 400 `VALIDATION_FAILED` と項目ごとのエラー（`errors`） |
| Service がエラーを返す（見つからない・権限なし） | 404・403 と、そのエラーの `code` |
| 形の違うリクエスト（JSON が壊れている・ID が数字でない） | 400 `MALFORMED_REQUEST` / `VALIDATION_FAILED` |

## 7. テストの書き方の決まり

- **名前**：日本語で「条件と結果」が分かるように書く（例：`期限ちょうどの行も期限切れとして削除する()`、`test('280文字ちょうどは投稿できる')`）
- **形**：準備 → 実行 → 確認 の3段。1つのテストでは1つのことを確かめる
- **境界値の並び**：同じ形で値だけ変えるケースは、`@ParameterizedTest`（JUnit）・`test.each`（Vitest）でまとめ、値の表として読めるようにする
- **時刻**：`Clock.fixed`（バックエンド）・引数で「今」を渡す（フロント）。実行する時刻で結果が変わらないようにする
- **データ**：テストごとに必要なものだけ作る。ほかのテストのデータに頼らない
- **偽物（モック）**：自分たちのコードの下の層だけを偽物にする（Service のテストでは Mapper、Controller のテストでは Service）。DB の動きは偽物にせず、Mapper のテストと結合テストで本物を使う
- **DB**：Testcontainers の使い捨ての PostgreSQL を使う。H2 は使わない（[README](../README.md)「テスト・整形チェック」）
- **置き場所**：バックエンドは対象と同じパッケージ、フロントは対象のファイルの隣（`〇〇.test.ts(x)`）
- **フロントの実行環境**：React（フック・部品）や `localStorage` などブラウザの機能を使うテストは、ファイルの先頭に `// @vitest-environment jsdom` を書く。それ以外は Node のまま（速い）
- **偽物の時計（フロント）**：必要なものだけ偽物にする（例：`vi.useFakeTimers({ toFake: ['setInterval', 'clearInterval'] })`）。`vi.waitFor` は待つ間に偽物の時計を少しずつ進めるので、時間の境界を確かめるテストの準備では使わない。`setTimeout` を偽物にするときは、Testing Library が内部で待てるよう `vi.stubGlobal('jest', { advanceTimersByTime: ... })` を置く（`SearchPage.test.tsx`）
- **ファイル全体で状態を持つモジュール**（`api/client.ts` のアクセストークンなど）は、テストのたびに `vi.resetModules()` と `import()` で読み込み直し、ほかのテストの状態を持ち越さない

### 9.9 段階 G（E2E テスト）の結果（2026-10-23）

部品ごとのテストでは、フロントは通信を偽物にし、バックエンドは画面を通さない。そのため「画面とサーバーを実際につないだときの食い違い」は確かめられていなかった。E2E テストを入れ、大事な流れに絞って確かめる。

| 流れ（`frontend/e2e/`） | 確かめること |
|---|---|
| 新規登録 → 投稿 → いいね → コメント（`post-flow.spec.ts`） | 画面から登録・投稿・いいね・コメントができ、読み込み直しても残っている。💬 から来たらコメント欄にフォーカス |
| ログイン・ログアウト（`auth.spec.ts`、3件） | 読み込み直し・新しいタブでもログインしたまま（HttpOnly の Cookie での再発行）。ログアウト後は入れない。パスワード違い・使われているユーザー名のエラー |
| 画像付きの投稿（`image-post.spec.ts`） | 画像を S3（LocalStack）に保存し、ブラウザがその URL から実際に読み込めている |
| フォロー（`follow.spec.ts`） | ヘッダーの検索 → プロフィール → フォローすると、その人の投稿がフォロー中のタイムラインに出る |

- **データの置き場所**：バックエンドは `./gradlew bootTestRun`（`TestBackendApplication`）で、単体・結合テストと同じ使い捨てのコンテナ（PostgreSQL・LocalStack）につないで起動する。開発用の DB には書き込まない。8080 番で開発用のバックエンドが動いていたら、使い回さずに起動の失敗にする
- **テストどうしの独立**：DB は実行全体で共有するので、テストごとに違うユーザーを作る。本題でない下準備（ほかの人の登録・投稿）は API で行う
- 実行：`cd frontend && npm run test:e2e`（6件・約20秒。初回はコンテナの取得とビルドで長くなる）。3回ずつ繰り返して（`--repeat-each=3`）18回すべて通ることを確かめた
- コードを4通りにわざと壊し（起動時に Cookie でログイン状態を取り戻さない・画像の URL を壊す・フォロー中のタブで全体を読む・コメント数を反映しない）、すべて落ちることを確かめた
- CI では別のジョブ（「E2E テスト（Playwright）」）で動かす。失敗したら、操作の記録（trace）と画面の写真を保存する

### 9.10 CI での扱い

今は基準を下回っても CI を落とさない（フロントが基準に届いていないため）。各段階で基準に届いたら、その層の基準を CI で守る（JaCoCo の `jacocoTestCoverageVerification`・Vitest の `coverage.thresholds`）かを決める。
